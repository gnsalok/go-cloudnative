# Istio mTLS Workshop Demo

This workshop now demonstrates both:

- East-west mTLS: `frontend` -> `backend` service-to-service traffic inside the mesh.
- North-south TLS/mTLS: external client -> Istio ingress gateway -> `frontend`.

The chart and app are designed for local Kubernetes (Docker Desktop).

Before running steps, read the mental model:

- `docs/MENTAL_MODEL.md`

## 1) What changed

- App refactor: `main.go` moved into `go-sample-app/` and supports two roles:
  - `frontend`: exposes `/call-backend` and calls the backend service.
  - `backend`: responds to `/`.
- Helm chart now deploys:
  - `frontend` Deployment + Service
  - `backend` Deployment + Service
  - optional `curl` pod for in-cluster testing
  - Istio `Gateway`, `VirtualService`, `DestinationRule`, `PeerAuthentication`
- New docs and cert assets:
  - `docs/certs/generate-local-certs.sh`
  - `docs/manifests/letsencrypt-*.yaml`

## 2) Prerequisites

- Docker Desktop with Kubernetes enabled
- `kubectl`, `helm`, `istioctl`
- Istio installed in-cluster (`istio-system` namespace)

If Istio is not installed yet:

```bash
istioctl install --set profile=demo -y
```

## 3) Build image and deploy app

Build image locally (Docker Desktop cluster can use local Docker images):

```bash
docker build -t go-sample-app:v1 .
```

Create namespace and enable sidecar injection:

```bash
kubectl create namespace go-app
kubectl label namespace go-app istio-injection=enabled --overwrite
```

Deploy with Helm:

```bash
helm upgrade --install goapp ./helm/go-sample-app -n go-app
kubectl get pods -n go-app
```

## 4) East-west mTLS demo (service-to-service)

`PeerAuthentication` is set to `STRICT` for this namespace, so plaintext is rejected and mesh mTLS is required.

Note:
The request URL is `http://...` at application level, but traffic on the wire is still encrypted with Istio mTLS between Envoy sidecars. In other words, this step demonstrates transport security via mesh mTLS, not application-managed HTTPS certificates.

Run request from in-mesh curl pod to frontend path that calls backend:

```bash
kubectl exec -n go-app deploy/goapp-go-sample-app-curl -- \
  curl -sS http://goapp-go-sample-app-frontend:8080/call-backend
```

Expected: response includes both frontend and backend details.

Verify workload certs and identity on sidecar:

```bash
istioctl proxy-config secret deploy/goapp-go-sample-app-frontend -n go-app
```

You should see a cert chain with SPIFFE identity (`spiffe://cluster.local/ns/go-app/...`).

## 5) North-south HTTPS demo (TLS termination at ingress)

### 5.1 Generate local certificates

```bash
./docs/certs/generate-local-certs.sh
```

This generates:

- `server.crt/server.key`: certificate presented by ingress gateway.
- `server-ca.crt`: CA that issued server cert.
- `client.crt/client.key` and `client-ca.crt`: for client-auth mTLS mode.
- Detailed file-by-file explanation: `docs/certs/README.md`.

### 5.2 Configure SIMPLE TLS on ingress

Create TLS secret in `istio-system` (same namespace as ingress gateway workload):

```bash
kubectl -n istio-system create secret tls go-app-tls \
  --cert=docs/certs/out/server.crt \
  --key=docs/certs/out/server.key \
  --dry-run=client -o yaml | kubectl apply -f -
```

Install chart with SIMPLE TLS values:

```bash
helm upgrade --install goapp ./helm/go-sample-app -n go-app \
  -f helm/go-sample-app/values-ingress-simple-tls.yaml
```

Port-forward ingress locally:

```bash
kubectl -n istio-system port-forward svc/istio-ingressgateway 8443:443
```

In another shell, call with SNI + trusted CA:

```bash
curl --resolve example.com:8443:127.0.0.1 \
  --cacert docs/certs/out/server-ca.crt \
  https://example.com:8443/
```

### 5.3 Why secret in `istio-system` and what each cert file is for

Why the secret is in `istio-system`:

- Istio `Gateway` uses `tls.credentialName` (for example `go-app-tls`).
- The ingress gateway workload (`istio-ingressgateway`) runs in `istio-system`.
- Envoy on ingress loads certs from Kubernetes secrets through SDS for that workload.
- So the referenced secret must be created in `istio-system` with the expected keys.

Why the SIMPLE TLS command uses `secret tls`:

- `kubectl create secret tls ...` stores:
- `tls.crt`: server certificate presented by ingress during TLS handshake.
- `tls.key`: private key matching that server certificate.
- This is enough for gateway mode `SIMPLE` (server-auth TLS).

Why MUTUAL mode needs extra CA material:

- In gateway mode `MUTUAL`, ingress also validates the client certificate.
- That requires trusted client CA cert in the secret (key `ca.crt`).
- In this demo, `go-app-mtls` includes `tls.crt`, `tls.key`, and `ca.crt`.

Certificate files generated by `docs/certs/generate-local-certs.sh`:

| File | Used by | Purpose |
|---|---|---|
| `server-ca.crt` / `server-ca.key` | Local signing step | Local CA that issues ingress server cert |
| `server.crt` / `server.key` | `go-app-tls` or `go-app-mtls` secret | Server identity presented by ingress gateway |
| `client-ca.crt` / `client-ca.key` | Local signing step and `go-app-mtls` secret (`ca.crt`) | CA trusted by ingress to verify client certs |
| `client.crt` / `client.key` | External client (`curl --cert/--key`) | Client identity for north-south mTLS |
| `server.csr`, `client.csr` | Local signing step | CSR inputs used to issue server/client certs |
| `server-ext.cnf`, `client-ext.cnf` | Local signing step | Extensions like SAN and EKU (`serverAuth` / `clientAuth`) |

Note:
This ingress secret-based TLS is for north-south traffic. East-west mTLS in Step 4 uses Istio-issued workload certificates from `istiod`, not these ingress secrets.

## 6) North-south mTLS demo (client cert required)

Switch gateway TLS mode to `MUTUAL`:

```bash
helm upgrade --install goapp ./helm/go-sample-app -n go-app \
  -f helm/go-sample-app/values-ingress-mtls.yaml
```

Create secret including server keypair and trusted client CA:

```bash
kubectl -n istio-system create secret generic go-app-mtls \
  --from-file=tls.crt=docs/certs/out/server.crt \
  --from-file=tls.key=docs/certs/out/server.key \
  --from-file=ca.crt=docs/certs/out/client-ca.crt \
  --dry-run=client -o yaml | kubectl apply -f -
```

Test without client certificate (should fail):

```bash
curl -vk --resolve example.com:8443:127.0.0.1 \
  --cacert docs/certs/out/server-ca.crt \
  https://example.com:8443/
```

Test with client certificate (should succeed):

```bash
curl --resolve example.com:8443:127.0.0.1 \
  --cacert docs/certs/out/server-ca.crt \
  --cert docs/certs/out/client.crt \
  --key docs/certs/out/client.key \
  https://example.com:8443/call-backend
```

## 7) How Istio manages workload certificates (east-west)

- Istio sidecars do not use your ingress TLS secret for in-mesh mTLS.
- `istiod` acts as the mesh CA by default and issues workload certs to Envoy via SDS.
- Workload identity is SPIFFE-based (`spiffe://cluster.local/ns/<ns>/sa/<sa>`).
- Default workload cert lifetime is 24h and certificates are rotated automatically.
- `PeerAuthentication` controls what inbound TLS mode a workload accepts.
- `DestinationRule` controls outbound TLS origination behavior from client sidecars.

In this demo:

- Namespace `PeerAuthentication` is `STRICT`.
- `DestinationRule` for backend explicitly sets `ISTIO_MUTUAL`.

## 8) About Let’s Encrypt and local `example.com`

Important limitation:

- You cannot realistically issue a Let’s Encrypt cert for `example.com` in local Docker Desktop.
- `example.com` is reserved and not under your DNS control.
- Let’s Encrypt requires domain validation (HTTP-01/DNS-01/TLS-ALPN-01).

So for local demo we use self-signed/local CA certs (from `generate-local-certs.sh`).

If you own a real domain (for example `app.your-domain.example`), you can use cert-manager + Let’s Encrypt:

```bash
kubectl apply -f docs/manifests/letsencrypt-clusterissuer.yaml
kubectl apply -f docs/manifests/letsencrypt-certificate.yaml
```

Then set in values:

- `istio.tls.credentialName: go-app-tls`

The certificate secret is created by cert-manager in `istio-system` and consumed by Istio gateway.

### Who is the certificate issuer?

- Local demo issuer: your local CA cert (`server-ca.crt`) created by OpenSSL script.
- Let’s Encrypt flow: issuer is Let’s Encrypt intermediate CA (for example `R3`), chaining to ISRG root.
- Mesh workload certs: issuer is Istio CA (`istiod`, or your configured external CA) for SPIFFE identities.
